## Pièges et leçons (maintenance permanente)

> **Instruction permanente** : noter au fil de l'eau, directement dans la liste ci-dessous, chaque piège ou découverte importante rencontré pendant le développement (endpoint, DOM, ordre de données, regex de build, etc.). Une entrée = une règle courte et actionnable, ajoutée sous la bonne section. Les leçons générales de conception restent dans les docs, on ne copie que le piège.

### API OpenCode / OpenChamber (instance réelle)

- **Le listing `/api/session/:id/message` est paginé aussi** (fenêtre par défaut, 41 premiers messages vus en pratique sur 136) : avec `order=asc` sans `limit`, les derniers tours (là où sont les `answer` et les rendus) disparaissent du diagnostic et on conclut à un appel manquant. TOUJOURS `?limit=200` sur ce listing quand on inspecte une session.

- **`/api/session` est paginé à 50 par défaut**: au-delà de 50 sessions de l'instance (avec tous les enfants compagnon/sous-agents), les parents glissent dans et hors des 50 premières à chaque création → « fantômes » alternatifs dans la flotte et flicker des cartes. TOUJOURS paginer `/api/session?limit=200` (ou paginer explicitement).

- L'ordre des messages est **descendant** (plus récent d'abord) : `.slice(-n)` prend les plus anciens: toujours trier sur `time.created` avant usage.
- **Le prompt humain est à la RACINE du message** (`m.text`) sur l'API installée, pas dans `payload.text` (ancienne forme) : lire `m.text ?? m.payload.text` (helper `daemon/src/messages.mts`), sinon le compagnon ne voit aucun message utilisateur, son « objectif » reste `inconnu de l'extrait` et ses résumés ne parlent que de la sortie de l'agent.
- `/api/session/:id/message?limit=N&order=asc` renvoie les **plus anciens** messages (défaut : desc). Utile pour retrouver le premier prompt sans paginer, et sans dépendre de la fenêtre des 30 derniers (un long tour fait sortir le prompt de la fenêtre).
- Le marqueur `completed` d'un message assistant arrive **en retard** : filtrer sur `completed` pour décider qu'une réponse est lisible = faux négatif. Vérifier que le texte tient debout (p.ex. parse JSON du compagnon).
- Un tour en cours = souvent des tool calls **sans texte** : pour savoir ce qui se passe, lire la part `reasoning` du dernier assistant.
- `POST /api/session/:id/prompt` **ignore le champ `agent`** sur la version installée. Pour changer d'agent : `POST /api/openchamber/sessions/:id/send` avec `{prompt, agent, directory}`: directory **requis** (dossier du parent).
- Session enfant avec `parentID` = masquée automatiquement de la flotte (filtre `parentID`) → utilisé pour les sessions compagnon.
- `/api/sessions/status` (OpenChamber) contient des **ids fantômes** (sessions supprimées) → joindre à l'annuaire `/api/session` et filtrer les absents ; les archivées (`time.archived`) sortent de la flotte.
- Le port local d'OpenChamber n'est **pas fixe** (auto-alloué) : discovery par `ss -tlnp` sur le process `openchamber`, ou `OPENCHAMBER_PORT`.
- **Sur Windows, `discover.mts` plante au démarrage du daemon** (`Executable not found in $PATH: "ss"`) : `ss` n'existe pas, passer impérativement `OPENCHAMBER_PORT` (port du process principal `OpenChamber.exe`, trouvé par `Get-NetTCPConnection -OwningProcess <pid>` ; les autres `OpenChamber.exe` qui écoutent sont des services d'extensions).
- OpenCode server direct = Basic auth détenue par OpenChamber : **toujours passer par OpenChamber**.
- **Une session entre dans « In work » du home dès qu'un message lui est envoyé**, quel que soit son dossier (`metadata.openchamber.work.state = open`, module `session-work`). Le chat superviseur vit dans `~/.superviseur` et y apparaît quand même : retirer le marqueur avec `POST /api/openchamber/sessions/:id/metadata` `{patch:{openchamber:{work:null}}}` après création et après chaque send. Changer le dossier ne règle pas ce point.
- **Un steer admis pendant un tour n'est promu qu'au PROCHAIN pas de l'agent** (`SessionInput.promoteSteers`, appelé au début de chaque tentative de tour dans le runner OpenCode) : après l'annulation d'une question, l'agent reprend et lit le message à son pas suivant ; un modèle peut reposer une question en course avant de lire le steer (le message reste admis, il sera livré, mais il n'apparaît dans le listing qu'au moment de sa promotion). Ne pas conclure à un envoi perdu tant que le tour n'est pas terminé.
- **OpenChamber queue : `POST /api/message-queue/sessions/:id/items/:itemId/take` retire l'item et renvoie son contenu COMPLET** (pièces jointes avec `dataUrl`, omises des snapshots) ; les boutons « Modifier » et « Envoyer maintenant » d'OpenChamber sont les deux gestes `take` (+ prompt steer). La queue ne tient que quand la session est busy : à l'idle, OpenChamber dispatche les items immédiatement.
- **Suppression de session via proxy** : `DELETE /api/session/:id` renvoie 204 (session totalement détruite, enfants compagnon inclus). Pour une fermeture douce qui garde l'historique, archiver plutôt (`POST /api/openchamber/sessions/archive` `{ids:[]}`).
- **Aucune API OpenChamber ne crée un enfant avec un dossier choisi** (testé le 2026-11-10, y compris avec prompt) : `POST /api/session` avec `parentID` hérite TOUJOURS du dossier du parent (`directory` ignoré) ; `POST /api/openchamber/sessions` honore `directory` mais ignore `parentID` (l'enfant devient une conversation de premier niveau, visible partout : essayé puis REVENNU EN ARRIÈRE le jour même sur décision du propriétaire, « pire qu'avant » dans le tiroir de sessions). Un `directory` de session existante n'est pas modifiable (PATCH ignoré). État retenu : comp./verif. = enfants `parentID` dans le dossier de leur tâche (imbriquées, repliées sous la tâche) ; seul `/api/fleet/create` pose un `directory` (défaut `SUPERVISOR_DIR`) pour les créations sans projet. Si un jour OpenChamber accepte `parentID` + `directory`, la création de comp./verif. dans `.superviseur` pourra être reprise (voir l'historique du commit 69b81d7).
- **Erreur/retry OpenCode : le status poll ne les expose pas** : `/api/sessions/status` ne porte que `idle|busy` ; écouter le SSE `session.execution.failed` et `session.retry.scheduled` (erreur dans `data.error`, tentative dans `data.attempt`), puis effacer l'état sur `session.execution.started|succeeded|interrupted` ou `session.inbox.enqueued`.
- **Un retry ne relance pas `session.execution.started`** (cet événement marque le début du tour, pas de la tentative) : effacer « Nouvel essai » seulement sur la fin de tour laissait le bandeau rate limit pendant tout le travail rattrapé (constaté le 2026-11-08, plusieurs minutes). `session.retry.scheduled` porte `data.at` = heure de reprise : le signal est périmé dès que `now >= at` (`SessionIssueTracker.get`), et un nouvel échec repousse l'échéance.
- Les scheduled tasks n'ont **pas d'historique de runs** ; `/api/openchamber/message-search` existe (à tester) ; la mémoire agent = JSON lisible-corrigeable via HTTP.
- **Livraison inline : le dernier message assistant n'est pas la réponse** : un tour finit souvent par des tool calls sans texte. Depuis le dernier message `user`, prendre le dernier texte assistant et le dernier `openchamber_render` du même tour.
- **`openchamber_render`** : la page est dans `state.input.parameters.html` (ou `state.input.html`), le titre dans `parameters.title` (ou `title`), et le rendu est confirmé par `state.metadata.openchamber.ok`. Les pages en langage `ui` (`parameters.ui`) ne sont pas du HTML : ne pas les dessiner comme telles.
- **Plan de tâche** : le plugin **SuperviseurPlan** (`daemon/plugin/superviseur-plan`, référencé dans `~/.config/opencode/opencode.jsonc` depuis sa migration hors de `OpenCodeTodoList` ; renommé `todo*` → `plan-*` le 2026-11-07) écrit son JSON dans `opencode.db`, table `kv`, clé `plugin:…:session/<sessionID>`. La lecture stable pour le daemon est le tool part (`planwrite` et `planupdate`, `state.metadata.items`, chaque tool part porte la liste complète), pas la base ; la table `todo` native n'est pas ce store. Le lecteur (`daemon/src/plan.mts`) accepte aussi les tool parts anciens `todowrite`/`todoupdate` et la clé `todos` (sessions d'avant renommage).
- **`planupdate` met à jour par numéro, transactionnellement** : l'appel passe `{updates:[{num,status?,content?,priority?}]}` ; un état inconnu ou un numéro hors bornes refuse la mise à jour, sans réécrire la liste. Pas de repositionnement implicite : les numéros sont l'index du tableau de la liste.
- **Numéros et affichage superviseur** : la popup « Plan de la tâche » (`PlanPopover`) calcule `i+1` côté UI ; l'ordre du tableau du plugin est l'ordre affiché, aucun index persisté côté daemon.
- **File d'attente OpenChamber** : `POST /api/message-queue/sessions/:id/items` avec `{directory, item:{content,text,sendConfig}}`. `sendConfig` est **obligatoire** (`providerID`, `modelID`, `agent` éventuel) : le reprendre de `/api/session/:id` (`model.id` / `model.providerID`), sinon 400. `GET /api/message-queue` renvoie la file de toutes les sessions ; retrait par `DELETE /api/message-queue/sessions/:id/items/:itemId`. La file survit à la fermeture de l'onglet et se vide quand la session redevient idle.
- **Revert depuis un message** : `POST /api/session/:id/revert/stage` `{messageID}` puis `POST /api/session/:id/revert/commit` (204). `stage` seul ne supprime rien (marqueur réversible) ; il faut les deux. Abort le tour en cours avant, et restaurer le texte utilisateur dans le composer si on veut le même geste qu'OpenChamber.
- **Étapes du plan dans la flotte** : `plan` doit porter `steps:[{text,status}]` (source `planwrite`) en plus de `done/total`, sinon le popup n'a rien à lister. L'UI tolère un `plan` sans `steps` (vieux daemon) et ne doit jamais supposer le champ présent.
- **Publication de flotte : enrichir AVANT de publier (flicker du 2026-11-07)** : entre `buildFleet` et `enrichPlanProgress`, `cachedFleet` exposait des frames sans `plan` (progress du verdict au lieu du plan) ; choper par SSE 500 ms et poll 3 s, c'est la barre qui s'anime (38 % → 0 → 38 %) et la section Plan du détail démontée/remontée. Ne jamais publier un snapshot non enrichi ; détail dans `docs/analyses/mvp1/flicker-flotte-progress-plan.md`.
- **`/api/sessions/status` est une carte EN MÉMOIRE d'OpenChamber** (`session-runtime.js`, Map `sessionStates` alimentée par les seuls événements `session.status` du SSE d'OpenCode) : perdue au redémarrage d'OpenChamber ou d'OpenCode (une session au repos ne réémet jamais l'événement) et expirée après 24 h (`SESSION_STATE_MAX_AGE_MS`). Fermer le Superviseur ou redémarrer OpenChamber vidait donc le tableau alors que les conversations existent. La flotte ne se construit jamais sur ce seul statut : le registre persistant `fleet_seen` (`state.mts`) + `restoreFleetRows` (`fleet.mts`) notent chaque carte vue et remettent au tableau, à chaque poll, les conversations encore existantes ; `work=done`, archivée, supprimée (404 confirmé en lecture directe) et sous-session ne reviennent pas, et l'instance injoignable ne décide rien. Doc : `docs/analyses/mvp1/flotte-persistante.md`.

### Empaquetage Electron (.exe Windows, 2026-11-10)

- **electron-builder pend indéfiniment si le .exe de sortie est en marche** (« output file is locked ... waiting for unlock ») : fermer l'instance de test avant de rebuild.
- **Lancer electron-builder avec node, pas bun** : sous bun, la collecte `pm=bun` s'arrête en erreur et l'exécution reste bloquée sans enfant actif.
- **Le packer asar 26.18 n'embarquait pas package.json** (sanity check « corrupted » en échec, même avec `package.json` dans `files`) : `asar: false` retenu (l'app n'a pas de node_modules en production, le layout réel suffit).
- **La cible portable réextrait l'app à chaque lancement** (~140 Mo, ~15 s la première fois, cache ensuite) ; le dossier de données va dans `%APPDATA%\Superviseur` (`SUPERVISEUR_DATA_DIR`, stable même en portable). **Relancer le .exe pendant qu'une instance tourne fait quitter proprement la précédente** (remplacement par le launcher, jamais deux daemons) ; le verrou `requestSingleInstanceLock` reste le garde en dev.
- **Une écriture asynchrone sur un stdout coupé tue le main via uncaughtException (EPIPE)** : blinder `process.stdout`/`process.stderr` avec `.on('error')` dans le main Electron (le try/catch synchrone ne couvre pas l'erreur asynchrone).
- **Le daemon de supervision est lié à sa base** : une base fraîche (`%APPDATA%\Superviseur` pour l'app, un dossier de test) crée sa PROPRE conversation « Superviseur » dans `.superviseur` (`ensureSupervisorSession` lit `supervisor_session` de la base, ne scanne pas OpenChamber). L'app qui adopte un daemon déjà en marche n'en crée pas de deuxième.

### Modèles et configuration du chat (2026-11-08)

- **Catalogue des modèles** : `GET /api/model` renvoie `data[]` (garder les modèles de chat, `enabled !== false`, `status !== 'disabled'`), `GET /api/provider` donne les noms lisibles, `GET /api/agent` les agents (`mode === 'primary'`, `hidden` faux). **Un `type` absent vaut `chat`** : les modèles d'une source custom (Skytech, par exemple) n'ont pas de `type` et un filtre `type === 'chat'` seul les faisait disparaître du sélecteur alors que le modèle par défaut en venait (constaté le 2026-11-08) ; seuls les types explicitement non chat (`image`, `embedding`, `decision`) sont exclus. Les agents internes (`superviseur-orchestrateur`) ne sont pas des choix : les filtrer, sinon le chat perd ses outils. Cache de 30 s (`daemon/src/models.mts`) : ne pas relire 171 modèles à chaque poll, et redémarrer le daemon après un changement de filtre (le cache garde l'ancienne liste).
- **Changement à chaud** : `POST /api/session/:id/model` `{model:{providerID,id}}` et `POST /api/session/:id/agent` `{agent}` répondent 204 sur une session vivante, sans la recréer.
- **Préférences : NULL = défaut, et le défaut doit être appliqué** : `supervisor_pref` ne stocke que des refs `provider/model` et un id d'agent (aucun secret). Revenir à « défaut » ne suffit pas à remettre le modèle : il faut POSTer le modèle par défaut, sinon la session garde l'ancien.
- **Validation à l'enregistrement ET à l'usage** : une valeur absente du catalogue n'est pas stockée (repli + avertissement affiché dans le popover) ; une préférence devenue morte est ignorée au prochain envoi (`chatModelRef`) et `start_task` ne part pas avec une ref inconnue.
- **Agent choisi et nom fixe** : `ensureSupervisorSession` compare à l'agent choisi, pas au nom par défaut ; sinon chaque poll re-bascule l'agent et annule le réglage. Depuis le retrait du versionnage (2026-11-10), le défaut est `ORCHESTRATOR_AGENT` (nom fixe) ; un ancien nom versionné sur la conversation bascule en place une fois, jamais remplacée.
- **Le sous-titre du chat porte le modèle effectif** (`SupervisorState.model`), pas seulement le nom de l'agent : un réglage invisible ne se vérifie pas. Le popover de config est un portail `position:fixed` comme `PlanPopover` (l'aside du chat est `overflow-hidden`), et un `<select>` natif groupé par provider suffit pour 158 modèles.
- **Modèle par tâche : le réglage global ne sert qu'aux nouvelles tâches** : `supervisor_pref.task_model` est lu uniquement par `start_task` (via `resolveTaskModel`). Une tâche existante porte son modèle dans `task_brief.model` et `task_resume.model` ; `resumeTick` lit ce modèle puis `defaultModelRef()`, jamais `taskModelRef()`. Sinon changer le réglage global déplacerait toutes les tâches existantes à leur reprise.
- **`armTaskResume` ne met pas à jour `model` en conflit** : pour changer le modèle d'une tâche, passer par `updateTaskModel` (state.mts) qui écrit le brief ET le registre. Écrire seulement `task_brief` laisserait la reprise sur l'ancien modèle.
- **Détail d'une tâche : engrenage à gauche de la flèche OpenChamber** : `GET /api/fleet/model?sessionId=…` renvoie `model` (préférence), `effective` (session), `name` et le catalogue ; `POST /api/fleet/model` applique à chaud puis persiste. Le libellé du détail affiche le modèle EFFECTIF (`name`), le select du popover la PRÉFÉRENCE : les deux diffèrent quand aucune préférence n'existe, c'est normal. La valeur vide remet le défaut et efface la préférence ; une ref inconnue est refusée avant tout POST.
- **Un modèle de tâche se change sans recréer la session** : `POST /api/session/:id/model` répond 204 sur la session vivante ; le test `task-model.test.mts` vérifie qu'aucun `POST /api/openchamber/sessions` ne part. Un refus de la session (`apply_failed`) laisse le brief et le registre intacts, donc la reprise ne part pas sur un modèle que la session n'a jamais accepté.

### UI (patterns de la page flotte)

- **Le snapshot navigateur scopé sur un textarea lit le textContent, jamais la valeur** : un textarea contrôlé a toujours un textContent vide, donc « le brouillon est vide » n'est PAS une preuve. Vérifier le contenu du composer par un effet observable : le bouton Envoyer n'est activé que si le composer a du texte, ou par ce que l'envoi livre réellement.

- **Favicon : l'URL du head est versionnée, et il faut bumper `?v=` quand `ui/public/favicon.svg` change** : OpenChamber a déjà servi sur le port 5180 (auto-alloué) et la base Favicons de Chromium garde le bitmap d'une URL d'icône déjà vue, sans re-télécharger : l'onglet affichait l'hexagone OpenChamber sur `/fleet` alors que le serveur répondait 200 avec le bon SVG sous la MÊME URL `127.0.0.1:5180/favicon.svg` (constaté le 2026-11-09, diagnostiqué dans la base Favicons de Vivaldi). Le lien du head porte `?v=AAAAMMJJ` ; un curl ne reproduit jamais le symptôme (il contourne la base Favicons et le cache HTTP).

- `replaceChildren` **déplace même les nœuds identiques → blur** : ne mettre à jour le DOM que si l'ordre change (`setChildrenIfChanged`), et ne reconstruire une carte que si son « sig » change.
- Variables d'état dans les templates : ne pas composer un préfixe « : » à deux endroits (double `: :` réel). La variable porte déjà sa ponctuation, le template s'abstient.
- Le sig d'une carte doit inclure **tout ce qui doit rafRAÎCHIR à l'écran** (statut, id de formulaire, progress, comptes critères) sinon la carte semble figée (bug 95 % vs 100 %).
- Pendant une saisie (focus INPUT/TEXTAREA d'une carte), ne jamais reconstruire cette carte.
- Formulaire de questions : **multi-champs** (q0, q1 → un seul bouton Répondre) ; `type` variable (`string`, `multiselect` → valeur en TABLEAU) ; répondre par objet `{qN: ...}` complet. Le choix **« Autre »** porte le champ libre : il s'active dès la frappe (les options se désélectionnent) et envoie EXACTEMENT le texte saisi, jamais le libellé d'une option ; « Répondre » est bloqué tant qu'« Autre » est actif avec un texte vide ou en espaces, et choisir une option efface le texte libre.
- Menu contextuel : `position:absolute` exige un ancêtre positionné: `.card { position:relative }` sinon le menu s'ancre à la page.

### UI React (depuis la migration du 2026-11-06)

- La référence visuelle est `ui/reference/flotte-vanilla.html` (l'ancien `ui/index.html`) ; le code vit dans `ui/src`, le build dans `ui/dist` et `ui/index.html` n'est plus que l'entrée Vite. Ne jamais remettre de TS inline dans un HTML servi tel quel.
- **Tailwind v4 met `line-height:1.5` sur `html`** : la maquette validée est en `normal`. Garder `body { line-height: normal }` dans `src/index.css`, sinon tout le contenu descend de ~5 px et le rendu n'est plus identique.
- **Le squelette vanilla cachait trois éléments par construction** : le chip « attends ta réponse », la boîte permission et la ligne ✋ orange existent dans `cardHTML` avec `display:none`, et `applyState` ne les crée que s'ils sont absents. La référence ne les affichait donc jamais. React les rend (exigence du brief) : ne pas « corriger » React vers ce bug.
- **Une carte qui change de section est démontée/remontée par React** : le brouillon du composer vit dans le store Zustand (`drafts`), sinon le texte est perdu en passant EN COURS → BESOIN. Le focus peut être perdu à ce moment-là (comme avec `replaceChildren` en vanilla).
- **SSE et GET doivent pousser la MÊME flotte enrichie** : le SSE envoyait `currentFleet()` brut (sans `task` ni filtrage des fermées), le GET filtrait. Les cartes fermées côté daemon réapparaissaient à chaque frame SSE puis disparaissaient au poll suivant : flicker, ordre qui change, titres qui semblent se battre pour le même id. `enrichedFleet()` est maintenant partagé par `/api/fleet` et `/api/fleet/stream`.
- **`pollOnce` est single-flight** : GET /api/fleet, l'intervalle 3 s et les événements SSE déclenchaient des polls concurrents qui publiaient des snapshots dans le désordre (même session avec deux états). Les demandes concurrentes sont coalescées ; ne pas retirer ce garde-fou.
- **L'UI ignore un `fleet.at` plus ancien** que celui déjà affiché : un GET en retard ne doit pas écraser un frame SSE plus récent (garde dans `setFleet`).
- **Les frames SSE se répètent 2x/s à l'identique** : dédupliquer sur la chaîne brute (`ev.data`) avant `setFleet`, sinon re-render inutile deux fois par seconde.
- **Tailwind : deux utilitaires de la même propriété (`bg-green` + `bg-amber`, `font-medium` + `font-semibold`) ne se départagent pas par l'ordre de la classe** : toujours une classe conditionnelle exclusive.
- **`bun run build:ui` avant de lancer le daemon** : il sert `ui/dist` avec une table MIME (js/css/svg/woff) ; sans build, `/fleet` renvoie un 404 explicite.
- **Un job `busy` n'est jamais TERMINÉ** : l'état terminé est DÉTERMINISTE depuis le 2026-11-12 (plus de verdict de compagnon) : au repos + plan posé et à 100 % + tous les critères validés (`isDone` de `ui/src/lib/fleet.ts`) ; busy, attente, erreur et retry priment toujours.
- **Au repos sans travail complet, la carte passe en warning « à compléter »** (triangle orange, détail des manques : étapes du plan, critères validés) ; l'étoile mauve de « fini, à valider » a disparu. L'hystérésis de 8 s (`placement.ts`) reste : l'état est déterministe mais peut rebondir quand l'agent ajoute un critère ou une étape à la fin.
- **Livraison inline : jamais les messages dans la flotte** : `GET /api/fleet` et le SSE ne portent que l'état. L'UI appelle `GET /api/fleet/delivery?sessionId=…` pour une carte TERMINÉ ou au repos (pas busy, pas en attente), et seulement quand `lastUpdateAt`/`turnStartedAt` change. Cache daemon 30 s, invalidé par `message.*`, `session.execution.*`, `session.inbox.*`, `session.text.*`, `session.step.ended`, `session.idle`.
- **Rendu openchamber_render** : iframe `sandbox="allow-scripts"` sans `allow-same-origin` et CSP (`connect-src 'none'`, `form-action 'none'`). Jamais de HTML brut dans le DOM. Le markdown passe par `react-markdown` avec `skipHtml`, sans `rehype-raw`.
- **Mini chat OpenChamber en iframe** : l'absence de `X-Frame-Options` ne garantit pas l'embeddabilité. Vérifier le `Content-Security-Policy: frame-ancestors` HTTP de l'instance réelle ; le checkout utilise `OPENCHAMBER_FRAME_ANCESTORS`, appliqué au démarrage, donc une modification nécessite un redémarrage. Vérifier le header effectif après relance : l'environnement du processus Electron principal peut ne pas refléter celui du serveur qui émet la CSP. Le deep-link mini chat est `/mini-chat.html?mode=session&sessionId=…` ; la route répond 200 mais peut être bloquée par la CSP du serveur.
- **Images locales de la livraison** : le navigateur ne peut pas lire un chemin disque et l'UI n'est pas servie par OpenChamber. `DeliveryMarkdown` réécrit les sources locales vers `/api/fleet/asset` (chemin validé dans le dossier de session, raster only, 10 Mo). Une image refusée affiche un placeholder, jamais une icône cassée.
- **Tooltip : jamais en `position:absolute` dans la carte** : une bulle vit dans un portail `createPortal(document.body)` en `position:fixed`, `width:max-content` + `max-width`, position recalculée au scroll/resize et bornée à la fenêtre, ouverte au survol ET au focus clavier (`tabIndex`), `Échap` la ferme. (Constaté sur la bulle de confiance, dont le composant a été retiré le 2026-11-07 : la règle reste valable pour toute nouvelle bulle.)
- **Popup des étapes du plan** : le compteur `x/y` est un bouton ; la bulle vit aussi dans un portail `position:fixed`, sous le compteur, avec repli au-dessus si elle dépasse. Tant que le plan n'a pas commencé (aucune étape `completed` ou `in_progress`), afficher `N étapes`, jamais `0/N` : ce n'est pas une progression mesurée.
- **Tour en cours : Envoyer et Stop coexistent** : le composer n'est plus désactivé. Le carré Stop reste le bouton le plus à droite (à la place de l'envoi quand le champ est vide) ; dès qu'un texte est saisi, un bouton Envoyer apparaît à sa gauche et met le message dans la file. Ne pas revenir au seul Envoyer désactivé : l'écriture pendant un tour est une exigence.
- **Fermer le détail n'est pas fermer la tâche** : la clôture d'une tâche est `Terminé` (vert, sur la carte et dans le détail) ; le panneau de détail se ferme avec `Fermer le détail`. Un `Fermer` ambigu du détail a retiré une conversation de la flotte au lieu de fermer le panneau.
- **La tâche sélectionnée qui quitte la flotte glisse vers sa voisine** (celle au-dessus dans l'ordre affiché, sinon celle en dessous, sinon fermeture du panneau) : la décision vit dans `setFleet` et `closeSession` (même `set` que la disparition ; la calculer après coup dans un effet démonte l'`aside` le temps d'un frame et fait sauter la mise en page). Les candidates viennent de `visibleRows()` (filtre et tri de l'écran), jamais de `fleet.rows` brut, et une sélection nulle le reste (pas d'ouverture automatique).
- **Pied de carte : le deuxième bouton change de rôle selon l'état** : sur une carte busy c'est `Détail`, sur une carte terminée c'est `Terminé` (clôture immédiate, sans confirmation si aucune question). Ouvrir le détail d'une carte passe toujours par un clic sur la carte elle-même, jamais par ce bouton (déjà arrivé : un clic « pour voir le détail » sur une carte au repos a clôturé la tâche) ; pour rouvrir, `reopenTaskState` de `state.mts` remet `closed_at` et `closure` à NULL, et le marqueur `closed` côté UI ne vit qu'en mémoire (un rechargement l'efface).
- **La carte n'a plus de composer (2026-11-07, demande du propriétaire)** : l'écriture à une tâche passe par le détail ; `Composer.tsx` n'a plus que la variante auto-grow d'inspecteur, la carte est passée de 232 à 190 px (grille en trois rangées). Ne pas « régénérer » le composer de carte ; le brouillon du détail suit toujours le store (`drafts`).
- **Anneau de sélection en `ring-inset`** : les cartes collées aux bords du panneau rognent un `ring` extérieur ; `ring-inset` dessine à l'intérieur de la bordure. Un `line-clamp` avec `line-height` serré coupe aussi les jambages (p, g) : garder `1.45` et un `pb` de 2 px.
- **Visionneuse de preuves : tout vit dans `CriteriaSection`** : les captures (`evidence` de kind `screenshot` avec `path`) deviennent des boutons nommés « Agrandir la capture de preuve AC-nn » ; le lot traverse TOUS les critères de la tâche (clé `critère:rang` : un même fichier cité par deux critères reste deux entrées), et l'état du rang vit dans la section, jamais dans la flotte, la base ou `types.ts`. Le composant est en portail `document.body` : le détail n'est pas démonté, sa position de lecture est conservée. Navigation bornée partagée par les boutons et le clavier (`stepIndex`), pas de bouclage aux extrémités.
- **Échap et flèches de la visionneuse en phase de CAPTURE** : `TaskInspector` ferme le détail sur Échap avec un listener `document` en bulle ; sans `document.addEventListener('keydown', onKey, true)` + `stopPropagation()`, fermer la visionneuse fermait aussi le panneau. Et pas de repli sur un `onKeyDown` React du dialogue : après un clic sur un bouton devenu `disabled` (dernière image), le focus tombe sur `body`, hors du dialogue, les touches ne seraient plus reçues. Vérifié au navigateur (Échap : visionneuse fermée, détail ouvert, focus rendu à la miniature).

### Blocs openui-lang et questions du chat (2026-11-08)

- **Le rendu natif d'OpenChamber n'est pas importable** : son UI est privée et tire toute l'application. On réutilise donc le vrai parseur (`@openuidev/lang-core` 1.0.2) et son catalogue (`ui/src/openui/catalog.ts`, copie assumée d'OpenChamber 2.6.1), jamais un parseur maison. `UiBlock.tsx` ne dessine qu'un sous-ensemble ; tout autre composant retombe en code brut.
- **Normaliser avant react-markdown** : `fenceUiBlocks` (`ui/src/openui/taggedBlocks.ts`) transforme `<openui-lang>` et les fences ```` ```openui ```` en ```` ```openui-lang ````. L'appliquer dans `ChatMarkdown` ET `DeliveryMarkdown` (donc `answer` et résultat), sinon les variantes restent du texte.
- **Un override `code` seul ne suffit pas** : react-markdown garde le parent `<pre>`. L'override `pre` doit repérer l'enfant `code.language-openui-lang` et rendre `UiBlock` à la place ; un `div` dessiné dans `<pre>` produit du HTML invalide.
- **Repli brut, jamais vide** : bloc invalide, partiel (streaming) ou composant non dessiné (`BarChart`, `Choice`, `Input`, `Button`) affiche son source en code. C'est ce qui rend le streaming sûr et ce qui interdit de laisser un formulaire openui mort : une question passe par le tool `question`.
- **Une question vit dans les formulaires en attente, pas dans les tool parts** : `/api/sessions/status` `pending[sessionId].forms` filtré sur `metadata.kind === 'question'` ; `metadata.tool.messageID` rattache la carte au message (sinon elle s'affiche en fin de fil). `replyForm` et `cancelQuestion` (`/api/fleet/reply`, `/api/fleet/cancel-question`) acceptent la session de supervision sans ligne de flotte.
- **`renderToStaticMarkup` et Zustand** : un composant branché sur un store lit `getInitialState` au rendu serveur, donc `setState` est ignoré. Tester les sous-composants purs (`ChatQuestionCards`, `questionsForMessage`, `orphanQuestions`) plutôt que `SupervisorChat` entier.
- **Dépendances ajoutées** : `@openuidev/lang-core` et `zod`, celles d'OpenChamber. Elles pèsent sur le bundle (~690 kB brut, 210 kB gzip) ; c'est le prix du parseur natif, pas une dépendance décorative.

### Chat de supervision (2026-11-06)

- Le chat vit dans `~/.superviseur` (session OpenChamber normale, agent `superviseur-orchestrateur` à nom fixe). **Tout le dossier** est exclu de la flotte : les anciennes conversations restent dans OpenChamber mais ne deviennent jamais des cartes.
- **Plugin projet-local** : `~/.superviseur/.opencode/plugins/superviseur` est bien chargé ; un agent projet-local dans `~/.superviseur/.opencode/agent` n'est **pas** chargé par cette version d'OpenChamber. L'agent orchestrateur est donc global et à nom fixe.
- **Trust du dossier** : OpenChamber met le dossier en pause (`opencode_trust_required`) tant que son empreinte de plugins/commandes n'est pas approuvée. Le daemon appelle `GET/POST /api/opencode/trust` avec le `fingerprint` avant de créer la session.
- **Ajouter un plugin exige un redémarrage d'OpenCode** : `/api/location/reload` ne recharge pas la liste des plugins, et `/api/config/reload` peut interrompre une réponse en cours. Le dossier doit être approuvé puis OpenCode redémarré une fois.
- **Outils du plugin** : `codemode: false` pour des outils directs. L'agent désactive `openchamber*` et `execute`. Depuis le 2026-11-12, les tools de flotte sont globaux (plugin `superviseur-fleet`, plus de garde `not_supervisor` dessus) ; seules les lectures bornées d'investigation restent réservées au chat (plugin projet-local `superviseur`, garde `not_supervisor` + mode Investigation).
- **Mode Investigation** : les permissions du prompt et de l'agent ne suffisent pas. Le dispatcher `/api/tools/:name` doit appliquer l'allowlist selon le mode actif côté daemon ; les lectures de projet utilisent uniquement le dossier choisi côté serveur, des chemins relatifs et refusent les liens symboliques. Ne jamais ajouter `bash`, `webfetch` ou un outil natif sans garantie en lecture seule.
- **`start_task` et doublons** : la flotte peut ne pas avoir encore vu la nouvelle session. Vérifier `task_brief` (écrit immédiatement) et garder un set `creating` par `projet|titre` ; sinon deux appels rapprochés créent deux sessions.
- **Chat UI** : l'erreur d'envoi (`sendError`) est séparée de l'erreur de poll (`refreshError`) ; sinon le poll suivant efface le bandeau et fait disparaître le message. Composer actif pendant un tour busy (file d'attente), icône Envoyer identique aux cartes, auto-grow 120 px. Après « Nettoyer », rendre le focus au textarea quand `creating` repasse à false.
- **`send_task` dans le chat** : la puce dit « a envoyé un message à une tâche », mais le bloc sous la puce doit nommer la tâche. Le titre est **relu dans la flotte à l'affichage** (`taskTitleOf`), jamais figé dans le message : un renommage reste correct et une tâche sortie de la flotte donne « une tâche qui n’est plus dans la flotte ». Le texte envoyé vient de `metadata.text` et reste complet, sans troncature.
- **« Nettoyer » n'est pas un tour LLM** : le bouton vide le chat et crée une session sans prompt ; l'ancienne conversation reste visible dans OpenChamber. Séparer `creating` de `sending` ; l'écran se vide immédiatement, sans indicateur « le superviseur travaille ». Les suggestions de l'écran vide ont été retirées (demande utilisateur).
- **En-tête du chat** : la barre de page (logo, titre, « Masquer », Live) a été retirée ; le chat porte le titre. Icône balai seule avec infobulle « Nettoyer le chat » (l'ancienne conversation reste dans OpenChamber), icône de panneau pour replier, flèche pour OpenChamber. Replié, un rail de 34 px avec l'icône de panneau rouvre le chat.
- **`send_task`** : l'outil d'écriture dans une tâche (disponible à toute session depuis le 2026-11-12). Une question en attente est **annulée** via `DELETE /api/session/:id/form/:formID?message=…` puis le texte est envoyé (même geste qu'OpenChamber), TEL QUEL : l'encadrement OWNER_WRAP est retiré ; une permission reste bloquante. `cancel_question` et le bouton « Annuler la question » font le même DELETE. `close_task` refuse une attente sauf `force` explicite, et annule alors la question en journalisant l'abandon. Pas de `reply_task`, pas de `merge_pr`.
- **Information inaccessible = intention de tâche probable** : si le chat n'a pas l'accès (web, fichier, exécution), il ne répond pas seulement « je ne peux pas » ; il propose une tâche de recherche ou d'exécution, demande la précision minimale, et lance `start_task` sur accord. Une demande explicite (« cherche la météo à Montréal ») part directement dans le projet `chats` ; une question vague propose d'abord. Une question à laquelle il peut répondre reste une réponse.
- **Permissions : YOLO, hors scope** : l'instance ne demande pas de permission ; le chemin carte/proxy reste en place mais n'est pas développé. Voir `docs/analyses/mvp1/permissions-yolo.md`. Ne pas annuler une permission avec le DELETE des questions.
- **Changer le prompt de l'orchestrateur ne doit jamais remplacer la conversation** : le nom de l'agent est FIXE ; quand l'agent choisi change, `ensureSupervisorSession` garde la session et bascule son agent en place (`POST /api/session/:id/agent` `{agent}`, 204, historique intact). Recréer la session faisait « disparaître » le chat le 2026-11-07 : une tâche avait renommé `todowrite` en `planwrite` dans l'agent pendant que le propriétaire écrivait, le send partait dans l'ancienne session devenue orpheline et l'écran pointait une session vide.
- **`not_supervisor` se juge par dossier, pas par pointeur** : `isSupervisorSession` accepte toute conversation vivante de `~/.superviseur`, pas seulement `supervisor_session.oc_session_id`. Sinon une ancienne conversation rouverte dans OpenChamber (après « Nettoyer » ou une bascule d'agent) refuse tous les outils du chat.
- Détails, tests et questions : `docs/analyses/mvp1/chat-superviseur.md` et `chat-superviseur-tests.md`.

### Critères d'acceptation auto-gérés (2026-11-12)

- **Une seule source de vérité des transitions** : `daemon/src/criteria.mts` ; tous les tools criteria de l'agent (plugin `superviseur-criteria` → `POST /api/criteria/:name`) passent par ces fonctions. L'agent de la tâche est son PROPRE juge : `criteria_set_status` {ref, status: "validated" | "to_fix", note} applique le jugement (note = ce qui a été vérifié, ou la raison du refus, OBLIGATOIRE sur to_fix). Plus aucun flux vérificateur : le sous-agent est retiré, il n'existe aucun tool d'approbation côté daemon.
- **Honnêteté portée par les instructions, pas par un extérieur** : la description du tool et `composePrompt` (tools.mts) exigent une vérification RÉELLE avant « validated » et interdisent la validation « pour avancer » ; gelés par `daemon/test/criteriaGuidance.test.mts`.
- **« À valider » reste une porte à preuve** : seul `criteria_to_validate` mène à `to_validate` (au moins une preuve exigée, chemin contrôlé au dépôt : `evidence_path_missing` au tool, fichier du projet, relatif, sans lien symbolique). `criteria_set_status` ne pose jamais « à valider ».
- **Refs jamais réattribuées** : `task_state.criteria_seq` est un compteur qui ne décrémente jamais ; `criteria_remove` est une suppression DOUCE (`removed_at`, historique lisible via `include_removed`).
- **Version de contenu** : chaque preuve, jugement ou modification incrémente `version` ; une validation enregistre `validated_work` (JSON {commit?, at} du dossier projet) pour dater l'état validé (staleness affichable).
- **Le plafond de 12 critères porte sur les NON validés** : les validés sont de l'histoire, ils ne bloquent pas les ajouts ; une validation libère une place.
- **Tests critères : jamais la base de production** ; pattern des imports dynamiques + garde-fou de `criteria.test.mts` (les imports ESM sont hissés AVANT l'affectation d'env : sans import dynamique, deux runs de tests ont écrit AC-01..AC-14 dans la vraie base, nettoyés ensuite).
- **Le plugin criteria est chargé GLOBALEMENT : chaque agent de supervision doit désactiver explicitement les tools criteria dans son frontmatter** (déjà arrivé : un frontmatter laissait `criteria_list` actif, l'appel partait et revenait `not_task`, un appel perdu). Verrouillé par `daemon/test/criteriaGuidance.test.mts`. Le prompt est mis en cache par NOM : une session créée avant un changement de prompt garde l'ancien jusqu'au redémarrage d'OpenCode.
- **UI (retours du 2026-11-08) : les compteurs plan et critères partagent le MÊME gabarit** : barre `flex-1` plafonnée à 160 px (une largeur fixe divergente a été refusée par le propriétaire) et libellé `x/y` cliquable avec bulle portail (`PlanPopover` et `CriteriaPopover`, même mécanique) ; la liste critères de la bulle se charge à l'ouverture (la flotte ne transporte que les comptes).
- **Le commentaire se libelle selon le jugement** : « preuve refusée : (raison) » en orange sur « À corriger », « preuve acceptée : (note) » en vert sur « Validé », rien sinon.
- **Cliquer par sélecteur d'index dans la flotte peut fermer une tâche** (déjà arrivé : un `nth-of-type` a visé le menu ⋯ et « Fermer cette conversation » a clôturé la carte d'une autre tâche, en abandonnant sa question). Pour inspecter : cliquer la carte elle-même (`div[data-sid="…"]`) ou vérifier le `aria-label` du résultat. Une fermeture accidentelle se répare en remettant `closed_at`/`closure` à NULL ; la question abandonnée n'est pas rejouable.


### Auto-restart de tâche (2026-11-07)

- **La destruction d'une session n'est jamais lue dans le seul listing** : `/api/session?limit=200` peut cacher un id (pagination) et une instance lente peut répondre vide. Une session n'est déclarée détruite qu'après : absente de deux balayages consécutifs ET `GET /api/session/:id` en 404. Réponse 200 vide ou erreur réseau : on ne décide rien.
- **Toujours exiger une instance vivante avant toute reprise** (`liveIds` non vide) : une instance qui redémarre ne doit pas réarmer tout le registre d'un coup.
- **Archiver n'est pas supprimer** : une session sous `time.archived` est un geste humain, la reprise est désactivée (raison dans `task_resume.disabled_reason`), jamais relancée. **Une session archivée reste dans le listing `/api/session`** : c'est le filtre `!time.archived` qui la retient hors `liveIds` du tick, pas sa disparition du listing (sinon elle ressemble à un contact vivant et la reprise la traite comme vivante).
- **Le registre `task_resume` porte l'identité de la tâche** : `task_id` = session d'origine, `session_id` = session vivante courante. À chaque reprise, tout suit vers le nouvel id (`migrateTaskSession`) : brief, état de carte, journal, réponses et critères ; plus de verdict ni de mapping enfant depuis le retrait des sous-agents (2026-11-12).
- **Le modèle default courant vient de `GET /api/config/settings`** (`defaultModel`, celui du sélecteur de l'UI), repli `GET /api/model/default`. La session morte ne porte pas son ancien modèle. Sans modèle résolu : pas de départ en aveugle, l'essai est consommé et le backoff s'applique.
- **Créations refusées = essais comptés** : budget de 3 essais consécutifs, backoff croissant 30 s → 60 s → 120 s (plafond 10 min), budget remis à zéro après 10 min de session stable. Après épuisement, la tâche passe en désactivée. Une écriture humaine (`send_task`) réarme une tâche désactivée.
- **Interrupteur** : `SUPERVISEUR_AUTO_RESTART=0` désactive tout ; autres variables (essais, backoff, confirmation, fenêtre d'orphelines) dans `docs/analyses/mvp1/auto-restart.md`. Tests : `bun test daemon/test/resume.test.mts`.

### Tool `answer` (plugin superviseur-task, 2026-11-07)

- **Le tool `answer` n'est pas un banc d'essai** (déjà arrivé : une « vérification du rendu » envoyée comme réponse au propriétaire). La règle vit dans le **prompt injecté à la création de tâche** (`composePrompt` de `daemon/src/tools.mts`), car les tâches naissent dans des projets qui n'ont pas cette leçon dans leur AGENTS.md : ne pas compter sur le projet pour l'apporter. La description du tool (`daemon/plugin/superviseur-task`) porte le même garde-fou. Sans attente du propriétaire (question posée, point à valider, consigne livrée), rien à envoyer ; une validation de code ou de rendu passe par le build, les tests ou la flotte ; le bilan s'écrit en dernier message de session.
- **La réponse `answer` doit être autonome** (déjà arrivé : un `answer` en prose qui disait « le tableau du chat donne l'ordre complet » alors que le tableau vivait dans un `openchamber_render` de la session). ### Repo & docs

- **Backtick dans les commentaires SQL de `db.exec` (state.mts)** : tout le bloc est un template literal JS ; un backtick dans un commentaire SQL (même une ligne de doc) casse le parse de fichier entier avec une erreur d'astuce hors de l'endroit réel. Utiliser des guillemets français dans les commentaires SQL. (Récidive le 2026-11-08 avec la colonne signature de verifier_map : leçon relue puis reappliquée à l'identique.)
- **Lister le dossier avant d'attribuer un numéro de doc** (double 09 déjà arrivé).
- **`bun test daemon/test` en un bloc = verrous SQLite (2026-11-07)** : les fichiers de test ouvrent chacun `data/superviseur.db` (module `state.mts`) ; lancés en parallèle, les fichiers qui touchent la base (`resume.test.mts`, ...) échouent en bloc avec des erreurs `run (bun:sqlite)`, chacun isolément passe. Lancer fichier par fichier : `for f in daemon/test/*.test.mts; do bun test "$f"; done`. **Consequence réelle : un run batch a vidé les 5 tables `task_*` de la base de production le 2026-11-07** (les suppressions de `resume.test.mts` ont touché la vraie base, d'où le garde-fou dans le fichier de test qui refuse toute écriture si la base liée n'est pas temporaire). Ne jamais lancer en batch tant que le liage de `state.mts` n'est pas injectable.
- **`db` de `state.mts` a désormais `PRAGMA busy_timeout = 5000`** : un script ponctuel qui écrit pendant un tour du daemon ne tue plus le process avec `SQLiteError: database is locked` (déjà arrivé le 2026-11-07 : un `bun -e` de reconstruction a fait crasher le daemon sur `logEvent` de `companion.mts`).
- **Une demande de boîte à idées n'est pas un chantier d'implémentation** (déjà arrivé : « ajoute l'idée confiance non définie » lu comme « implémente-la »). Quand un message peut se lire comme une note de conception OU une tâche de code, trancher explicitement avant d'agir (question courte : « note dans la boîte, ou j'implémente ? »).
- **Image locale dans une réponse** : OpenChamber ne donne un grant que pour un chemin cité par le message assistant lui-même. Une copie du message dans un autre fil affiche une image brisée. Pour une image destinée à être partagée, servir une URL HTTP (build/daemon) ou une data URL, pas un chemin local.
